# 상용 배포 전 검수 (2026-07-31)

브라우저에서 **실제 UI 코드 경로**로 돌려 잰 결과. 코드를 읽고 추론한 것은 여기 적지 않는다 —
전부 재현 명령과 수치가 붙어 있다.

재현:
```bash
npm run check                       # 유닛 167 + 밸런스 게이트 + 스프라이트 알파(_raw·public/assets)
npm run build && npm run preview    # 프로덕션 번들로 검수한다(dev 서버는 HMR 이 끼어든다)
QA_URL=http://localhost:5184 npm run qa:launch          # 실제 브라우저 플레이 (~20분)
QA_URL=http://localhost:5184 node tools/capture.mjs     # 뷰포트 3종 스크린샷
npx vitest run tests/learning.spec.ts                   # 종단 학습 실측표
```

`qa:launch` 는 서버가 떠 있어야 하고 20분쯤 걸려서 `npm run check` 에 넣지 않았다.
**배포 전에 한 번은 돌린다** — 일시정지 중복 종료(1-2) 같은 버그는 여기서만 잡힌다.

## 1. 고친 것 (전부 실측 전/후 있음)

### 1-1. DDA 부호가 뒤집혀 있었다 — 막힌 아이에게 더 어려운 문제
`src/edu/mastery.ts` `pickLevel()` 이 `theta + ddaLevel * 70` 이었다. 주석에는
"DDA 단계당 쉬운 쪽으로"라고 적혀 있었으니 의도와 정반대다.

| | DDA 0단계 | 1단계 | 2단계 | 3단계 |
|---|---|---|---|---|
| A2 · θ1400 체감 정답률 | 0.83 | 0.78 | 0.72 | **0.64** |

두 번 연속 틀린 아이(=DDA 상승)에게 더 어려운 문항이 갔다. **화면에는 아무 표시도 안 난다** —
레벨은 프롬프트에 드러나지 않으므로 플레이로는 영원히 발견할 수 없었다.
상수를 `economy.ts` 의 `DDA_STEP_ELO` 로 통일했다(70을 두 곳에 적어 둔 것이 사고의 원인).
회귀 방지 = `tests/learning.spec.ts` 의 「DDA 단계가 오를수록 체감 정답률이 떨어지지 않는다」.

### 1-2. 일시정지할 때마다 rAF 루프가 하나씩 늘었다 — 주간 점수 부풀림
`loop()` 은 일시정지 중에도 맨 앞에서 자기 자신을 계속 예약한다(멈추는 건 시뮬 갱신뿐).
그런데 `togglePause()` 가 재개할 때 `requestAnimationFrame(loop)` 을 **한 번 더** 걸었다.
잠깐 버튼을 N번 누르면 사슬이 N+1개가 되고, 판이 끝날 때 `finish()` 가 N+1번 실행된다.

실측(프로덕션 빌드, 실제 브라우저):

| | 저장된 판 수 |
|---|---|
| 일시정지 0회 | 1 |
| 일시정지 5회 | **6** → 수정 후 **1** |

`edu.rounds`·`edu.playMs`·**주간 순위 버킷**이 같이 부풀었다. Esc 키도 같은 경로라
아이가 우연히 밟기 쉽다. 순위표에 치트 방어를 넣어 둔 제품에서 **클라이언트가 자기 점수를
N배로 만드는 경로**였다.
원인을 막은 뒤, 저장에 쓰는 경로라 `finish()` 자체에도 `finished` 잠금을 걸었다
(관문 화면이 이미 쓰던 방식) — 다른 이유로 두 번 들어와도 안전하도록.

### 1-6. "어디로도 보내지 않아요"가 조건 없이 적혀 있었다
주간 순위 동의 화면의 문구는 정확한데(별명·이번 주 숫자만, 이름/나이/학교/연락처 없음),
**메인 메뉴**와 **내 기록** 화면이 무조건 "기록은 이 기기에만 저장돼요 / 어디로도 보내지
않아요"라고 말했다. 순위 올리기를 켠 순간 거짓이 된다 — 특히 내 기록 표의 '푼 수'가
그대로 순위 점수로 나간다. 동의 상태에 따라 문구를 바꿨다.

### 1-7. 지도의 수문장 칸이 "× 10. 수문장"으로 읽혔다
`content: '⚔ '` — U+2694 는 기본이 **텍스트 표현**이라 얇은 선으로 그려져 작은 글씨에서
'×'로 보인다(실제 맥 크롬에서 확인). VS16(`⚔️`)로 그림 표현을 강제했다.
⚠️ **이 항목만 실기기 확인이 안 됐다** — headless 크롬에는 U+2694 이모지 커버가 없어
(🔒 는 그려지는데 ⚔️ 는 여전히 얇게 나온다) 수정 효과를 스크린샷으로 증명할 수 없었다.
이모지 폰트가 있는 기기(맥·아이패드·안드로이드)에서는 개선, 없으면 현상 유지라 되돌릴 이유는
없지만, 배포 전에 실기기에서 눈으로 한 번 봐 주면 좋겠다.

### 1-8. 새로 얻은 셈지기가 덱에 안 들어갔다 — 게이트가 볼 수 없는 사각지대
`prepScreen` 이 저장된 덱을 그대로 썼다. 1판에서 3기를 고른 아이는 **6판·8판까지 그 3기로**
싸운다 — 그 사이 4명을 새로 얻었는데도 칸 2개가 빈 채로.

실측(1판만 뛴 뒤 5판까지 진도를 넣은 저장 상태로 출전 화면 열기):
> 보유 카드 **7개** · 출전 버튼 **"출전! 3/5"** · 새로 얻은 붕붕이·먹도깨비(210)·옹기동이·붓통이 전부 미선택

아이 입장에서 "새 셈지기를 얻었다"는 보상이 전장에 아무 영향도 주지 않는다.
그리고 **밸런스 게이트는 이걸 영영 못 본다** — 프로브는 판마다 `buildDeck(보유 전부)` 로
최선의 5기를 새로 짠다. 게이트가 검증한 아이와 실제 아이가 달랐다.

빈 칸만 채우도록 고쳤다. 같은 상태에서 다시 재니 **출전! 3/5 → 5/5**.
고른 것을 빼지는 않는다. ⚠️ 다만 "일부러 5칸을 안 썼다"와 "새 셈지기를 못 봤다"를
구분하지는 못한다 — 구분하려면 저장에 '일부러 뺐음'을 기록해야 한다(스키마 변경).
2학년이 칸을 일부러 비워 둘 가능성보다 새 셈지기를 못 보고 지나칠 가능성이 훨씬 크다고 보고
채우는 쪽을 택했다.

이게 브라우저 하네스가 6·7·8판을 진 원인이었다. 프로브 표는 같은 구간에서 정답률 60%에도
100% 승리라고 말했는데, 그 간극이 정확히 덱이었다. **같은 조건으로 다시 돌린 결과:**

| 판 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 승률 |
|---|---|---|---|---|---|---|---|---|---|
| 수정 전 | 147초 | 152초 | 241초(잘림) | 73초 | 80초 | **패 2%** | **패 1%** | **패 1%** | 4/8 |
| **수정 후** | 69초 | 73초 | 64초 | 71초 | 72초 | **승 100%** | **승 100%** | **승 100%** | **8/8** |

(퍼센트 = 그 판에서 내 성 체력이 가장 낮았던 순간. 수정 후에는 8판 내내 한 대도 안 맞았다.)
판 시간도 64~79초로 균일해져 프로브 모델(ST1 @80% = 69초)과 맞는다.
1판은 보유가 3명뿐이라 여전히 "3/5" 다 — 채울 게 없으면 억지로 채우지 않는다.

**남는 질문 하나는 따로 쟀다.** 덱이 5칸을 채우고 나면 그 뒤 해금(해태장군 9판·장승 25판)은
빈 칸이 없어 여전히 자동으로 안 들어간다 — 아이가 출전 화면에서 직접 바꿔야 한다
(결과 화면이 "새 셈지기가 합류했어요!"로 알려는 준다). 그러면 **한 번도 안 바꾼 아이는
캠페인을 깰 수 있나?** 프로브에 임시로 '5판 덱 고정' 옵션을 넣어 재 봤다:

| | 일반 판 정답60% 최저 승률 | 보스(10·20·30) |
|---|---|---|
| 판마다 최적 덱 | 86% | 95 / 95 / 95% |
| **5판 덱으로 끝까지** | **86%** | **95 / 95 / 95%** |

차이 없음 — 전 게이트 통과한다(freeze 가 실제로 다른 시뮬을 도는 것도 확인: ST30 63초/19문 vs
68.5초/20문). 값비싼 유닛은 정답률 60%에서 어차피 자주 못 내기 때문이다. **그래서 덱 교체를
강제하거나 자동 교체하는 장치는 넣지 않았다.** 실험 코드는 측정 후 되돌렸다.

### 1-9. 스프라이트 알파 게이트가 CI에 없었고, 넣어도 헛돌 뻔했다
지난번 사고(배경 제거가 스프라이트 6개를 갉아먹은 채 배포됨)를 막으려고 만든
`tools/asset-check.mjs` 가 **`npm run check`(로컬)에만** 물려 있었다. 로컬에서 안 돌리면 그대로 나간다.

CI에 넣으려다 두 가지가 더 나왔다.

1. **검사 대상이 `_raw` 인데 `_raw` 는 커밋되지 않는다.** 그대로 CI에 넣었으면 "파일 0개"로
   **통과**했을 것이다 — 안 도는 것보다 **도는 척하는 쪽이 더 나쁘다.**
   실제로 배포되는 `public/assets/*.webp`(45개, 커밋됨)를 검사하도록 바꿨다.
   덤으로 **빌드 단계가 망가뜨린 경우까지** 잡힌다 — 지난 사고가 정확히 그랬다.
2. **파이썬이 이 컴퓨터의 venv 에 못 박혀 있고, 없으면 `exit 0`(통과)이었다.**
   출력만으로는 "게이트가 돌았다"와 "게이트가 자기를 껐다"가 구분되지 않았다.
   → 인터프리터를 `GUGU_PY` → 로컬 venv → `python3` 로 찾고,
   못 돌리면 **exit 1**. 일부러 건너뛰려면 `ASSET_CHECK_OPTIONAL=1` 을 명시해야 한다.

세 경로 다 실측 확인: 정상 0 / 파이썬 없음 1 / 명시적 스킵 0.

### 1-10. 밸런스 프로브가 실제보다 후한 아이를 상정하고 있었다
`DDA_STEP_ACC = 0.10` — 프로브는 막힌 아이에게 **단계당 정답률 +10%p(최대 +30%p)** 를
줬다. 실제 게임의 DDA 는 문항 *레벨*을 낮추는데, 사다리가 좁아 대부분의 아이가 이미 레벨 1
(바닥)이라 내려갈 데가 없다 → 실제 보정은 **0**.
0으로 바꿔 다시 돌려도 **전 게이트 통과**(일반 판 정답60% 최저 승률 90% → 86%,
보스 100% → 95%). 표가 실제보다 후하게 나오는 쪽이 훨씬 위험하므로 0으로 둔다.

## 2. 사용자 질문에 대한 실측 답

### "문제도 다양하게 나오는 거 맞지?"
**맞다.** 30판 660문항에 서로 다른 식 **257개**. 한 판 안에서 같은 식이 절반 넘게
반복되는 판은 **0개**. 실제 브라우저 플레이(8판 연속, 정답률 85%)에서도
한 판 19~23문항 중 서로 다른 식이 16~22개 — 판 안에서 거의 안 겹친다.

### "단계도 무한대고?"
**맞다.** `stageDef` 는 index 하나로 결정되며 5000판에서도 정의가 성립한다(발산·0·스폰 없음 0건).
캠페인 30판 이후는 적만 판당 ×1.05 로 세지고, 부족한 전력은 소환·승급으로 메운다.
도달 한계(승률 50% 이상) = 소환 0 → ST50, 전설 확보·승급 → ST60.

### "지금은 너무 쉬운데 나중에는 좀 어려워지기도 하지?"
**어려워진다.** 문항 유형이 3판마다 하나씩 열려 28판에 11종이 전부 열린다.

| 판 | 1 | 4 | 7 | 10 | 13 | 16 | 19 | 22 | 25 | 28 |
|---|---|---|---|---|---|---|---|---|---|---|
| 새로 열리는 갈래 | 한 자리 덧셈·뺄셈 | 받아올림 덧셈 | 곱셈구구 2~5단 | 받아내림 뺄셈 | 두 자리 ± 한 자리 | 곱셈구구 6~9단 | 나눗셈 | 두 자리 ± 두 자리 | 두 자리 × 한 자리 | 나머지 있는 나눗셈 |

1판은 한 자리 덧셈·뺄셈뿐이고, 28판은 3~4학년 과정인 나머지 있는 나눗셈이다.

## 3. 안 고친 것 — 사람이 정해야 하는 문제

### 3-1. ⚠️ 난이도 사다리가 좁아 목표 정답률에 아무도 도달하지 못한다
설계 목표는 L1(전투 중) 정답률 **0.85**(유창성)다. 실측:

| 아이 (그 단원 대비) | 1~10판 | 11~20판 | 21~30판 | 쓰인 레벨 |
|---|---|---|---|---|
| −200점 (아직 못 배움) | 18% | 24% | 22% | 전부 Lv1 |
| −100점 | 33% | 35% | 35% | 전부 Lv1 |
| **+0점 (막 배운 아이)** | **51%** | **50%** | **50%** | 전부 Lv1 |
| +100점 | 63% | 60% | 61% | 전부 Lv1 |
| +200점 (능숙) | 78% | 72% | 73% | Lv1 632 / Lv2 28 |

두 가지가 동시에 보인다.

1. **레벨 2~5가 사실상 안 쓰인다.** 660문항 중 Lv2 이상은 0~28개.
   유형별 5레벨이라는 조절 손잡이가 돌아가지 않는다.
   ⚠️ **브라우저 하네스에서는 반대로 보인다** — 거기선 레벨이 8판에 평균 2.19까지 오른다.
   두 모델이 다른 아이를 상정하기 때문이다. 하네스의 자동 플레이어는 **문항이 어려워져도
   정답률이 85%로 고정**이라 θ 가 천장 없이 올라가고 레벨이 따라 올라간다. 진짜 아이는
   어려워질수록 더 틀리므로 θ 가 실력에서 멈춘다 — 그래서 **실제 능력을 고정한
   `tests/learning.spec.ts` 쪽이 난이도 판정에 맞는 모델**이다. 하네스의 레벨 수치를
   "적응이 잘 되고 있다"는 증거로 읽으면 안 된다.
2. **그 단원을 막 배운 아이가 50%** — 밸런스 게이트가 가정하는 최저 정답률 **60%에도 못 미친다.**
   교육 모델과 밸런스 모델이 서로 다른 아이를 상정하고 있다.

원인은 산수로 딱 떨어진다. p=0.85 를 맞추려면 문항이 아이보다 **302 Elo 아래**여야 하는데,
`difficultyOf = baseB + (level−1)*60` 은 위쪽으로만 **240**밖에 안 펼쳐진다.
가장 쉬운 레벨 1조차 아이보다 **위**에 있으니, `pickLevel` 은 늘 레벨 1을 고를 수밖에 없다.

**한 줄 지렛대**: `src/edu/curriculum.ts`
```ts
return meta.baseB + (level - 1) * 60;    // baseB … baseB+240 (위로만)
// →
return meta.baseB + (level - 3) * 150;   // baseB−300 … baseB+300 (아이를 가운데 둔다)
```
예상 효과: 막 배운 아이 50% → 약 85%, 아직 못 배운 아이 22% → 약 60%,
레벨 1~5가 모두 쓰이고 **DDA 가 비로소 실제로 발화한다**(지금은 바닥이라 no-op).

**하지만 이건 게임 체감 난이도를 통째로 바꾼다.** 실제 정답률이 50%→85%로 오르면 셈력 수급이
크게 늘어 게임이 쉬워진다. 밸런스 게이트 전면 재실행 + "얼마나 어렵게 둘 것인가"라는
사람의 판단이 필요하다. 그래서 **오늘은 손대지 않았다.**
`tests/learning.spec.ts` 가 이 표를 매 실행 찍고, 현상을 characterization 으로 못 박아 둔다
(사다리를 고치면 그 단언이 깨져 반드시 눈에 띈다).

### 3-2. ⚠️ "L1에는 새 개념을 넣지 않는다"가 코드로는 지켜지지 않는다
`src/edu/session.ts` 첫 주석:
> 🔴 L1에는 **새 개념을 넣지 않는다.** … 새 유형 도입은 L2(관문)에서만 한다.

그런데 `quizTypesFor()` 는 `pool[pool.length-1]`, 즉 **가장 최근 열린 유형**을 항상 넣고,
전투(L1)와 관문(L2)이 **같은 `stage.quizTypes` 를 그대로 쓴다**. 28판이면 그 판에 처음
열린 '나머지 있는 나눗셈'이 전투 중에 바로 나온다. 3-1의 정답률 하락에 직접 기여한다.

선택지는 둘 중 하나이고, 어느 쪽도 그냥 고를 일이 아니다.
- **코드를 문서에 맞춘다**: L1은 관문에서 한 번이라도 만난 유형만 낸다(어떤 유형을 이미
  소개했는지 저장에 기록해야 한다 — 스키마 변경 + 진도 페이싱 변화).
- **문서를 코드에 맞춘다**: "새 유형도 전투에서 바로 낸다"로 고치고 3-1로 난이도를 잡는다.

덱을 고치자 판이 짧아졌다(3판 241초 → 64초). 당연한 결과지만 **부작용이 같이 온다**:

# 2차 — 실사용 보고 대응 (2026-07-31, 같은 날 저녁)

사용자가 직접 1판을 플레이하고 네 가지를 보고했다. 전부 재현·계측했다.
계측 근거는 `t=88초` 스크린샷 + 브라우저 계측 타임라인.

## 7-1. ⚠️ "먹대포가 발사가 안 되는데?" → **적이 없어서 아무 일도 안 일어났다**

대포는 정상 충전된다(t=36초에 fill 100%, `disabled=false`, `ready` 클래스). 문제는 **쏠 대상**이었다.

```
t초 적성%  아군 적군 전선(맵1000) 대포
 24  100%   19    1    874       -
 28   98%   23    0    964       -     ← 적군 0마리
 36   88%   29    0    964      READY  ← 불은 들어오는데 때릴 게 없다
```

`fireCannon()` 이 **살아 있는 적에게만** 피해를 줬다. 전선이 적 성까지 밀고 올라가면 화면에
적이 한 마리도 없는 시간이 길어서, 그때 누르면 **충전만 사라지고 아무 일도 안 일어났다.**
정답 12개로 번 것이 아무것도 아닌 게 되면 "모든 쾌감 장치는 정답의 하류에 둔다"는 원칙이 깨진다.

→ 대포가 **적 성에도** 피해를 준다(`CANNON_CASTLE_SHARE = 0.03`, 성 체력의 3%).
전 게이트 통과, "소환 무의미"도 유지(캠페인 ST50 / 전설 ST60 격차 그대로).

## 7-2. ⚠️ "적군이 안 나오는 거니? 나오자마자 죽는 거니?" → **후자다**

적은 `x = MAP_LEN`(적 성 자리)에 스폰되는데 아군 20~54기가 `x = 964`에 눌러앉아 있어서
**스폰과 동시에 죽는다.** 게다가 `die` 이벤트를 **아무도 소비하지 않아** 죽는 표시조차 없었다
(`core.ts` 가 push 하지만 `battle.ts` 는 `hit`/`castleHit` 만 읽었다).
적이 나타나 0.3초 만에 흔적 없이 사라지니, 아이 눈에는 "안 나온다"가 맞다.

→ 쓰러진 자리에 먹 자국을 남긴다(`FieldRenderer.puff`, 420ms, `reduceMotion` 이면 생략).
밸런스는 한 줄도 안 건드린다.

## 7-3. ⚠️ "우리 애들이 많이 쌓여서" → 아군 상한 60 → **16**

한 판에 아군이 **54기**까지 쌓였다(`allyCap: 60`). 화면이 스프라이트로 덮이고 개별 유닛이
아무 의미가 없어진다. 스윕 실측(예산 고정, 상한만 변경):

| 아군 상한 | 일반60% 최저 승률 | 보스(10·20·30) | ST5 문항 | 게이트 |
|---|---|---|---|---|
| 60 (기존) | 86% | 95/95/95% | 22문 | 통과 |
| 22 | 86% | 95/95/95% | 28문 | 통과 |
| **16 (채택)** | **86%** | **95/95/95%** | **32문** | **통과** |
| 12 | 81% | 95/95/90% | 34문 | 통과 |

상한을 낮추면 게이트는 그대로인데 **한 판 학습량이 22 → 32문항으로 늘어난다**(§3-3 의
"학습량이 하한에 붙어 있다" 걱정도 같이 해소된다). 12는 승률이 눈에 띄게 떨어져 16을 택했다.
덤으로 `syncDeck` 에 **"전장이 가득"** 사유를 추가했다 — 상한이 60일 땐 닿을 일이 없었지만
16에서는 자주 닿고, 안 그러면 셈력도 충분한데 눌러도 아무 일이 없는 **7-1과 똑같은 버튼**이 된다.

## 7-4. ⚠️ "아직도 성 체력이 초기인데 너무 세" → 성 체력 계수 42000 → **25000**

1판은 **성 : 적군 체력이 9:1** 이었다. 즉 한 판의 90%가 "무저항 체력바 갈기"다.

| 판 | 1 | 5 | 10 | 20 | 30 |
|---|---|---|---|---|---|
| 성 : 적군 | **9.0:1** | 8.5:1 | 4.0:1 | 2.7:1 | 2.2:1 |

**먼저 시도했다가 버린 안 두 개** (전부 실측으로 기각):

1. **성 → 적군으로 체력 이동**(총량 유지, 9:1 → 3.3:1 / 1.7:1 / 1.0:1):
   **전부 G2 FAIL.** 일반 판 60% 최저 승률이 86% → 67% → 62% → 43% 로 무너진다.
   성은 되받아치지 않지만 적군은 때린다 — 같은 체력이라도 위험도가 전혀 다르다.
2. **후반은 고정하고 초반 물량만 증량**(ST30 예산을 고정하고 ST1 만 올림):
   역시 **전부 FAIL** — 기울기를 눕히면 중반(ST5~25)이 무너진다.

남은 지렛대는 성 체력이었다. 상한 16 기준 스윕:

| 성 체력 계수 | 1판 성 체력 | 일반60% 최저 | ST5 문항 | 게이트 |
|---|---|---|---|---|
| 34000 | 17000 | 86% | 29문 | 통과 |
| 28000 | 14000 | 86% | 26문 | 통과 |
| 23000 | 11500 | 86% | 24문 | 통과 |
| 19000 | 9500 | 86% | 22문 | **FAIL**(학습량) |

23000이 바닥이라 여유를 두고 **25000** 채택 → 1판 성 체력 **21000 → 12500 (−40%)**.

## 7-5. 난이도 사다리 — 요청받아 고쳤다 (§3-1 해소)

`difficultyOf` 를 `baseB + (level−1)*60` → `baseB + (level−3)*150` 으로 바꿔
**아이를 사다리 한가운데** 세웠다(`baseB±300`).

| 아이 (단원 대비) | 이전 | **이후** |
|---|---|---|
| −200점 (아직 못 배움) | 22% | **61%** |
| −100점 | 35% | **73%** |
| **+0점 (막 배운 아이)** | **50%** | **84%** |
| +100점 | 61% | **90%** |
| +200점 (능숙) | 73% | **93%** |

설계 목표 0.85 에 정확히 올라앉았다. 레벨 2가 실제로 쓰이기 시작했고(660문항 중 97~136개),
**DDA 도 이제 진짜로 작동한다**(0.85 → 0.93). `tests/learning.spec.ts` 의 characterization
단언 두 개를 **원래의 엄격한 단언으로 되돌렸다** — 격차가 닫혔으므로.

🔴 **이 과정에서 테스트 자체의 결함을 하나 잡았다.** 아이 실력을 `difficultyOf(t, 1)` 기준으로
잡아 놨더니, 사다리를 넓히자 **아이 실력도 같이 움직여** 정답률 표가 한 자리도 안 변했다.
기준을 `difficultyOf(t, LEVEL_MID)`(=단원 표준 난이도)로 바꿔야 변화가 보인다.
자기참조 지표는 "고쳐도 그대로"로 보이게 만든다.

## 7-6. 못 고친 것

**전선이 적 성에 닿은 뒤의 무저항 구간은 남아 있다.** 1판 기준 24초까지는 적이 나오고
전선도 움직이지만(166 → 876), 그 뒤로는 성을 깎는 시간이다.
이건 "정답률 60%인 아이가 소환 없이 캠페인 30판을 전부 깬다"는 **설계 보증의 직접적 결과**다 —
적을 실제로 위협적으로 만드는 안은 위 두 가지 모두 그 보증을 깨뜨렸다(실측).
지금 한 것은 그 구간을 **짧게(성 −40%)**, **읽히게(죽는 표시)**, **덜 어수선하게(상한 16)**
만든 것이다. 구조를 바꾸려면 그 보증부터 다시 정해야 한다.

# 8. 3차: "적군이 성 안에서 나오다가 맞아서 안 보이는 거 아니냐" (2026-08-01)

사용자 질문 그대로: *"아군이 성을 공격하는 거랑 … 적군이 성 안에서 중간에서 나오면 …
성보다 적군이 더 앞으로 나오면 적군을 때리면 적군이 보이지 않아?"*

**맞았다.** 추측이 아니라 좌표 문제였고, 세 가지가 정확히 겹쳐 있었다.

## 8-1. 원인 — 성 그림이 전투 구역을 덮고 있었다

렌더러가 성 스프라이트를 월드 끝점에 **중심 정렬**해 그렸다(`x = cx - w/2`).
성 스프라이트는 월드 단위로 **195칸(맵 전체의 19.5%)** 이라, 그 안쪽 절반이 전투 구역을 통째로 덮었다.

900×480 캔버스 실측:

| | 월드 좌표 | 어디에 그려지나 |
|---|---|---|
| 적 성 스프라이트 | **902.7 ~ 1097.3** | — |
| 적 스폰 지점 | **1000** | 성 그림 **한가운데** |
| 근접 아군 정지점 | **963** | 역시 성 그림 **안쪽** |

아군이 963에 서는 이유: 성 타격 판정이 `|1000 − x| ≤ 사거리`인데 근접 사거리가 38이라
963에서 멈춘다. 그래서 아군도 적도 검은 성 그림 위에 겹쳐 그려졌다.
사용자 스크린샷에서 짚신이가 성에 파묻혀 보이던 게 이것이다.

## 8-2. 원인 — 적은 태어난 자리에서 한 픽셀도 못 움직이고 죽는다

`combat()` 은 사거리 안에 유닛이 있으면 이동 분기(`else if (u.spd > 0)`)를 아예 타지 않는다.
아군이 963에 서 있으면 적(1000)과 거리 37 → 스폰 즉시 교전 상태가 된다.

ST1 실측(`npx vite-node tools/enemy-visibility-probe.ts`):

| 등장 | 생존 | 최전진 위치 | 성에서 나온 거리 |
|---|---|---|---|
| 3.0초 | 10.60초 | x=705 | 295px |
| 11.9초 | 5.90초 | x=843 | 157px |
| 20.7초 | 1.53초 | **x=1000** | **0px** |
| 29.6초 | 0.87초 | **x=1000** | **0px** |
| 38.4초 | 0.83초 | **x=1000** | **0px** |
| 47.3초 | 0.67초 | **x=1000** | **0px** |

즉 **3번째 적부터는 성문 앞에서 1초도 못 버티고, 그 1초가 전부 성 그림에 가려 있었다.**
"안 나오는 거니, 나오자마자 죽는 거니"는 — 나오자마자 죽는데 그게 안 보인 것이다.

## 8-3. 고친 것 (전부 렌더러 — 밸런스 수치 0 변경)

1. **성을 전장 밖에 세운다.** 성의 **안쪽 면**이 월드 끝점이 되도록 바깥으로 밀었다
   (`castleBox()`). 성문 앞이 전부 빈 땅이라 교전이 그대로 보인다.
2. **성 크기를 가로폭도 보고 정한다.** 예전엔 높이만 봐서(`min(160, h*0.5)`) 좁고 높은
   화면에서 성 하나가 가로폭의 37%를 먹었다. 이제 `min(160, h*0.5, w*0.18)`.
3. **성문 등장 표시**(`spawn` 이벤트 → `gate()`). 적이 나오는 순간 성문에서 빛이 번지고
   발밑에 먼지가 인다. 죽는 자리 표시(`puff`)와 짝이다 — 나오는 순간과 쓰러지는 순간이
   둘 다 보여야 "나왔다가 맞고 쓰러졌다"가 한 장면으로 읽힌다.
   `spawn` 은 그리기 전용 이벤트라 시뮬 수치에 영향이 없다.

**실측 확인**
- 성문 빛: 성문 지점 픽셀의 R−B 값이 기준 19 → **114**(6배). 실제로 그려진다.
- 밸런스 불변: `일반 판 정답60% 최저 승률 86%` — 수정 전과 **같은 값**.
- 게이트: 202 테스트 전건 통과, 전 밸런스 게이트 통과, 스프라이트 위반 0건.
- 화면: 데스크톱 1280×800 / 태블릿 834×1112 / 휴대폰 가로 844×390 — 콘솔 에러 0건,
  세 곳 모두 적이 성 밖 빈 땅에서 교전하는 것을 눈으로 확인.

## 8-4. 회귀 방지

`tests/field-geometry.spec.ts` — 7개 화면 크기 × 5개 불변식(35 테스트).
성 그림의 안쪽 모서리를 **월드 좌표로 되돌려** 전투 구역을 침범하지 않는지 잰다.

🔴 공식을 테스트에 복붙하지 않았다. 렌더러가 **실제로 쓰는** `castleBox()` 를 호출한다.
   (공식을 옮겨 적으면 아무것도 검증하지 못한다 — §5에서 이미 한 번 밟은 함정이다.)
   되돌려 확인: `castleBox` 를 옛 중심정렬로 바꾸면 **14건 FAIL**
   (`expected 880 to be greater than or equal to 999.5`).

## 8-5. 남는 것 — 적 물량 자체는 여전히 적다

ST1은 63초에 적 7마리, 스폰 간격 8.8초다. 이건 그림 문제가 아니라 예산 문제다.
"정답률 60% 아이가 소환 없이 캠페인을 통과한다"(G2)는 보장이 적 총 체력을 묶고 있고,
**적을 잘게 쪼개 수를 늘리는 안은 못 쓴다** — `hpMul` 은 체력만 나누고 공격력은 그대로라
마릿수를 2배로 하면 들어오는 피해가 2배가 된다(G2 붕괴). §7-4에서 성→적군 체력 이전과
초반 물량 증가를 각각 스윕해 전부 FAIL 한 것과 같은 벽이다.

지금 상태에서 화면에 적이 있는 시간은 표본 기준 **37% → 75~89%** 로 올라갔다(전선 위치에
따라 다름). 이건 물량이 늘어서가 아니라 **보이게 돼서** 그렇다. 더 늘리려면 G2 보장 수치
자체를 사람이 다시 정해야 한다.

# 9. 4차: "너무 쉬워서 노잼" — 적응형 난이도 (2026-08-01)

사용자 보고: *"근데 지금은 너무 쉬운 것 같아.. 게임이 그래서 약간 노잼이야."*

## 9-1. 진단 — "쉽다"가 아니라 **"긴장이 0"** 이었다

승률 게이트는 전부 통과인데 재미가 없었다. 승률은 결과고 재미는 과정이라, 과정을 쟀다
(`tools/tension-probe.mjs`, 21시드 × 9판 × 정답률 4구간).

| 정답률 | 진 판 | 우리 성이 맞은 판 | 아슬아슬하게 이긴 판 |
|---|---|---|---|
| 40% | 35% | 38% | 3% |
| 60% | 4% | 7% | 1% |
| **80%** | **0%** | **0%** | **0%** |
| **95%** | **0%** | **0%** | **0%** |

**잘하는 아이 378판 중 우리 성이 한 대라도 맞은 판이 0개.** 이길지 질지가 아니라 구경이었다.

## 9-2. 손잡이가 하나도 안 들었다 — 구조 문제였다

| 시도 | 결과 |
|---|---|
| 적 체력 ×1.6 / ×2.2 / ×3 / **×4** | 정답80%+ 승률 **100% 그대로**, 성 피격 0% |
| 스폰 간격 ×0.5 / ×0.3 / ×0.2 / **×0.1**(몰려오게) | 성 피격 0% → 22%, 승률은 거의 그대로 |
| 적 공격력 ×3 | 정답40% 아이가 89% 패배(안전망 붕괴)인데 정답95% 아이는 **0% 패배** |
| 적 공격력 **×7** | 정답95% 아이 여전히 **0% 패배** |

원인: **되먹임에 반대 힘이 없다.** 잘 맞힐수록 셈력↑ → 유닛↑(상한 16) → 신바람↑ →
더 빨리 죽임 → 더 여유롭게 답함. 그리고 상비군 16기가 길목을 완전히 막아서
적 체력·물량을 아무리 올려도 **성문 앞에서 16대1로 죽을 뿐**이었다.
→ 숫자 하나로는 못하는 아이와 잘하는 아이를 동시에 못 맞춘다.

⚠️ **요약통계가 분포를 가린 사고**: 처음엔 21판의 *중앙값* 성 체력을 봤다. 결과가 0% 아니면
100%로 갈리는 분포라 중앙값이 그 사이를 통째로 지웠고, 어떤 배율에서도 "아슬아슬 0건"이
나와 손잡이가 안 듣는 것처럼 보였다. **판 단위로 세고 나서야** 무엇이 듣는지가 보였다.

## 9-3. 고친 것 — 적응형 난이도 단계 0~8 (`src/sim/tier.ts`)

사용자 선택: 돌파형 적 + 광역 공격 + 적 공격력 상향, 안전망은 **적응형 자동 조절**,
문항은 **전투 중 목표 정답률 하향**. 넷을 **단계 하나**에 묶었다.

| 단계 | 0 | 2 | 4 | 6 | 8 |
|---|---|---|---|---|---|
| 적 공격력 | ×1.0 | ×2.6 | ×4.8 | ×7.8 | ×11.6 |
| 돌파형 비율 | 0 | 25% | 42% | 58% | 70% |
| 광역 반경 | 0 | 70 | 100 | 130 | 160 |
| 문항 목표 정답률 | 0.85 | 0.82 | 0.79 | 0.77 | 0.77 |

- **돌파형** = 전선과 교전하지 않고 지나쳐 우리 성으로 직행. 상비군이 길목을 막는다는
  전제 자체를 깬다 — 원거리·빠른 셈지기를 뽑을 이유(=덱의 의미)가 여기서 처음 생긴다.
  발밑 화살표 + 머리 위 삼각형으로 표시한다(색만으로 구분하지 않는다).
- **광역** = 뭉친 아군을 쓸어버린다. "16기 쌓고 방치"를 정면으로 무력화.
  느리고 단단한 적·수문장에게만 준다(빠른 잡몹까지 광역이면 전선이 즉사한다).
- **조정 규칙** = 여유롭게 **2판 연속** 이기면 +1, **한 판만 져도** 즉시 −1. 비대칭이 의도다.
- 결과 화면이 바뀐 사실을 알려 준다(조용히 바뀌면 "왜 갑자기 어렵지"만 남는다).

### 🔴 안전망은 설계상 보장된다

**0단계 = 종전 밸런스와 완전히 동일**(배율 1.0 · 돌파 0 · 광역 0 · 목표 0.85)하게 만들었다.
적응 루프는 **이긴 아이만** 올리므로 어려워하는 아이는 0단계를 벗어나지 못한다 →
G2가 검사하는 그 밸런스를 그대로 만난다. `tests/tier.spec.ts` 가 0단계에 조미료가
새어 들어가지 않는지 감시한다.

## 9-5. 회귀 방지

  않는 천장**이다(그 조건 패배율 83% → '벽'으로 FAIL). 재야 할 건 **적응 루프가 아이를

## 9-6. 의도한 상충 — 아군 상한과 돌파형

아군 상한이 16이라, 전선에 16기를 다 채워 둔 상태에서는 **돌파형이 새어 들어와도 새로
소환할 수 없다**(덱 카드에 "전장이 가득"이 뜬다). 이건 버그가 아니라 대가다 —
"다 밀어 넣고 방치"가 지배 전략이 아니게 만드는 게 이번 변경의 목적이었다.
돌파형의 대응 수단은 두 가지이고 둘 다 덱에서 온다: **원거리 셈지기**(지나가는 놈을 쏜다)와
**여유분을 남기는 운용**이다.

⚠️ 다만 아이 눈에는 "위급한데 버튼이 안 눌린다"로 보일 수 있다. 실측상 승률은 유지되지만

  다 못 끝낸 판을 쉬워지게 하는 건 맞는 방향이고, 문구도 어긋나지 않는다. 조치 안 함.

### 남겨 둔 판단 — 난이도 카드가 자주 뜬다 (실측)

Gemini가 지적한 진동을 재 봤다. 승급은 "여유 2연승", 강등은 "1패 즉시"라 비대칭이어서
(승,승,패)가 반복되면 단계가 계속 오르내린다.

| 아이 실력 | 30판 중 난이도 변경 | 그중 방향이 뒤집힌 횟수 |
|---|---|---|
| 정답 40% | 0.0회 | 0.0회 |
| 정답 60% | 1.2회 | 0.7회 |
| 정답 75% | 11.0회 | 6.5회 |
| 정답 85% | **13.9회** | 6.1회 |
| 정답 95% | 10.4회 | 2.3회 |

잘하는 아이는 **두 판에 한 번꼴로** "세졌어요 / 약해졌어요" 카드를 본다.
단계가 ±1로 흔들리는 것 자체는 적응 루프가 경계를 찾는 정상 동작이고, 안전망(1패 즉시 강등)은
일부러 그렇게 만든 것이라 **비대칭을 없애면 막힌 아이를 붙잡아 두게 된다.**
그래서 규칙은 건드리지 않았다. 손을 댄다면 규칙이 아니라 **안내 빈도**(되돌이일 땐 카드를 접기)가
먼저 볼 손잡이다. 아이가 실제로 어떻게 읽는지는 교실에서 봐야 판단할 수 있다.

# 10. "적이 아예 안 나온다" — 두 번 오진한 버그

실사용자(교사)가 같은 증상을 **두 번** 보고했다. 두 번 다 렌더 문제로 봤고, 두 번 다 틀렸다.

## 10-1. 첫 번째 오진 — 성 그림 (8절, 실제로 있던 문제)

성 스프라이트가 전투 구역을 덮고 있었다. 이건 실재했고 고쳤다(커밋 `fe8c6a0`).
그런데 그걸 고친 뒤에도 사용자는 같은 말을 다시 했다. **증상이 남았다는 건 원인이 더 있었다는 뜻이다.**

## 10-2. 진짜 원인 ① — 적이 나올 자리가 없다

적은 월드 1000(성문)에서 나오고, 근접 아군은 사거리 38이라 962에 선다.
화면상 **23px**. 스프라이트 폭은 60~90px이다 — 적이 나오는 자리가 아군 더미 안쪽이다.

전선이 적 성에 닿은 뒤 스폰된 적을 전수 추적한 결과:

| | ST1 | ST5 | ST12 |
|---|---|---|---|
| 그 뒤 죽은 적 | 6기 | 11기 | 14기 |
| 평균 생존 | 0.88초 | 0.75초 | 1.62초 |
| **한 픽셀도 못 움직인 적** | **6/6** | **11/11** | **14/14** |

**31기 전원이 한 발짝도 못 떼고 죽었다.** 렌더 문제가 아니라 시뮬 문제였다.

→ `ALLY_CEIL_GAP = 90`. 적의 `enemyFloor`(아군 전선을 60 넘게 못 파고든다)와 **대칭인 상한**이다.
통로 끝에 선 아군은 사거리가 짧아도 성을 때린다(`atCeil`) — 이 예외가 없으면 근접 셈지기가
성에 못 닿아 판이 영원히 안 끝난다. `tests/spawn-corridor.spec.ts`가 그 조건을 직접 검사한다.

## 10-3. 진짜 원인 ② — 적 총량이 판 중간에 마른다

사용자가 "성 앞에 모이면"이라고 한 시각과 스폰이 마르는 시각이 겹친다.

| 판 | 적 총량 | 마지막 스폰 | 판 끝 | **적이 한 마리도 안 나오는 시간** |
|---|---|---|---|---|
| ST1 | 9기 | 65초 | 67초 | 2초 |
| ST3 | 16기 | 51초 | 79초 | 28초 (35%) |
| ST5 | 18기 | 60초 | 87초 | 27초 (31%) |
| ST12 | 22기 | 56초 | 121초 | **65초 (54%)** |
| ST20 | 23기 | 60초 | 119초 | 59초 (50%) |

12판은 **판의 절반 이상이 무저항 구간**이었다. 원인은 두 시계가 안 맞는 것이다 —
스폰 상한은 `적 HP 예산 ÷ 마리당 체력`으로 정해지는데, 판이 끝나는 조건은 **적 성 체력 0**이다.

⚠️ 이게 "너무 쉽다"의 진짜 원인이기도 했다. 9절에서 적 체력 ×4, 스폰 몰아치기 ×10을 걸어도
효과가 없었던 이유가 여기 있다 — **총량을 키워도 다 쓰고 나면 똑같이 빈다.**

→ 예비대(`RESERVE_SHARE = 0.25`, `RESERVE_COVER = 0.85`): 총량 중 뒤쪽 25%는 시간이 아니라
**적 성 진행도**에 묶어 배출.
`stages.ts`가 명시한 "무한 반복 = 느릴수록 불리해지는 죽음의 나선" 제약을 지키려면
**총량을 늘리면 안 된다.** 예비대는 언제 나오는지만 바꾼다.

### 튜닝 이력 — 재배치만으로는 반드시 쉬워진다

처음엔 `RESERVE_SHARE = 0.5`, 배출 곡선을 진행도 1.0까지로 뒀다. 결과는 **게이트 3건 실패**,
그것도 전부 "너무 쉽다" 쪽이었다(찍기 통과 판 8→14개, 무한구간 도달 ST50→ST60).

이유는 두 가지다.
- 진행도 1.0에서 풀리는 예비대는 **성이 무너지는 순간** 나와 사실상 안 싸운다 → `RESERVE_COVER = 0.8`.
- 더 근본적으로, **미룬 적은 플레이어가 가장 강할 때 도착한다.** 총량이 고정이면
  재배치는 반드시 난이도를 낮춘다. 그래서 비율을 0.5 → 0.25로 낮춰 균형점을 찾았다.

두 변경을 따로 켜 봐서 원인을 분리했다:

| 설정 | 정답40% 패배율 | 정답60% 최저승률 | 찍기 통과 판 | 게이트 |
|---|---|---|---|---|
| 원본 | 42% | 86% | 8개 | 통과 |
| 통로만 | 55% | 86% | 6개 | 통과 |
| 예비대만(0.5) | 12% | 95% | 16개 | **3건 실패** |
| **통로+예비대(0.25)** | 46% | 86% | — | **통과** |

# 11. 모바일 가로 레이아웃 — 숫자패드가 화면의 45%

실사용자: "지금 캐릭터를 드래그 하게 하네… 아래가 너무 찬다, 특히 모바일".

이 게임은 **가로 전용**이다(세로에서는 회전 안내가 뜬다). 그래서 세로에서 잰 수치는 의미가 없다 —
처음에 세로로 재고 원인을 잘못 짚었다. 가로(844×390, iPhone 14)에서 다시 쟀다:

| 칸 | 이전 | 필요 | 이후 |
|---|---|---|---|
| 셈지기 덱 | **188px** | 286px (5장) | **286px ✅** |
| 먹대포 | 52px | | 52px |
| 문제 | 194px | | 143px |
| **숫자패드** | **379px (45%)** | | **319px** |

원인은 두 겹이었다.
- `.control` 그리드에서 **덱만 최소폭 0**이라, 모자란 폭을 덱이 혼자 다 뒤집어쓴다.
- 패드 폭은 버튼 최소폭 × 6열로 정해지는데, 그 값이 `7vw`(844px에서 59px)로 박혀 있었다.
  ⚠️ 기본 규칙(`8.4vw`)이 아니라 **`max-height: 430px` 미디어 쿼리 안의 값**이 실제 적용값이다.
  기본 규칙만 고치고 측정했다가 아무것도 안 바뀌는 걸 한 번 겪었다.

44px는 저학년 터치 타겟 하한이라 그 아래로는 내리지 않았다. 대신 좁은 가로(≤820px)에서는
카드를 54→48px로 줄여 5장이 다 들어가게 했다.

측정 결과(전부 5장 전부 보임): 데스크톱 1280×720 · 태블릿 1024×768 · 아이패드 1194×834 ·
iPhone 14 가로 844×390 · 안드로이드 800×360 · 좁은 가로 740×360 · 초저높이 900×310.
⚠️ **568×320(2016년 SE 가로)만 여전히 잘린다** — 패드 289 + 대포 52 + 문제 112 를 빼면
덱에 85px밖에 안 남는다. 그 폭에 5장을 넣으려면 카드가 터치 타겟 아래로 내려가야 해서 포기했다.

# 12. 없던 연출 — 원거리·먹대포·뽑기

실사용자: "먹대포 이펙트는 여전히 없음", "원거리 공격에서 뭐 날아가는 것도 안 보이는데",
"뽑기 할 때 이펙트가 너무 없어서 심심함", "똑같은 애가 나오네??".

전부 사실이었다. 코드를 확인한 결과:

- **원거리**: 사거리는 실제로 작동한다(청룡 250 vs 짚신이 38). 그런데 시뮬이 즉시 체력을 깎고
  렌더러에 투사체를 그리는 코드가 **아예 없었다**. 제자리에서 0.18초 흔들릴 뿐이었다.
  → hit 이벤트에 `from`(쏜 위치)을 실어 렌더러가 포물선으로 날아가는 먹덩이를 그린다.
  **그리기 전용이라 밸런스에 영향이 없다** — 맞은 결과는 이미 시뮬에서 났다.
- **먹 대포**: 전용 연출이 없었다. 화면 흔들림 4px + 기존 피격음이 전부였다.
  정답 12개를 모아 쏘는 이 게임 최대의 보상인데 화면에서 아무 일도 안 일어났다.
  → 우리 성에서 먹물 파도가 금빛 앞머리를 달고 전장을 쓸고 간다(620ms).
- **뽑기 중복**: `조각 +6` 태그는 있었지만 **그게 뭘 위한 건지, 얼마나 남았는지**가 없었다.
  아이 눈엔 그냥 꽝이다. → `조각 +6` + `5레벨까지 3개` / `5레벨로 올릴 수 있어요!`.
  ⚠️ 겸사겸사 버그 하나: 결과 카드가 레벨을 **항상 Lv.1로 하드코딩**하고 있었다(4레벨까지
  키운 셈지기를 뽑아도 Lv.1로 보였다).
- **뽑기 연출**: 전부 220ms 간격으로 똑같이 넘어가 전설도 잡몹처럼 지나갔다.
  → 유니크 이상은 620ms 뜸을 들이고 금빛 테가 퍼진다.

검수는 실제 브라우저에서 숫자로 확인했다(화면을 눈으로 세지 않는다):
투사체 15발 · 먹대포 1발 · 유니크 이상 연출 4장 · 조각 안내 표시 확인.
그러려고 렌더러에 `shotsFired`/`sweeps` 카운터를 두고 `window.__gugu__.fx`로 노출했다.


# 13. 교차검증(FULL) 2회차 — 세 계열이 각각 다른 걸 잡았다

라우터가 FULL을 지시했다(`crit=1`). codex·Gemini·code-reviewer 병렬.
판정: **codex REQUEST_CHANGES · Gemini 로직 APPROVE/카피 REQUEST_CHANGES · Claude APPROVE**.
CRITICAL 0건. 아래는 **전부 내가 직접 재현한 것만** 적는다.

## 13-1. 고친 것

**① 만렙 중복이 없는 레벨을 안내한다** (Gemini·codex 공통, 재현됨)
`canUpgrade`는 만렙과 조각 부족을 **구분하지 않고** 둘 다 `false`를 준다. 그걸 "부족"으로 읽으면
보통 등급(최대 5레벨·뽑힐 확률 55%)이 5레벨에 닿는 순간부터 영영 이렇게 뜬다:

```
1번째 중복 → "6레벨까지 5개"
2번째 중복 → "6레벨까지 1개"
3번째 중복 → "6레벨까지 1개"   ← 6레벨은 존재하지 않는다
```

가장 흔한 등급에서 가장 먼저 터지는 경로였다. → `이미 최고 레벨이에요`.

**② 10연에서 같은 셈지기가 두 번 나오면 첫 카드가 두 장 몫을 보여 준다** (Gemini 추가 발견)
결과 화면이 저장을 한 번만 읽어서, 먼저 열리는 카드가 이미 배치 전체가 반영된 최종 조각 수를
표시했다("아직 모자란데 벌써 올릴 수 있대"). → 뽑기 **전** 상태를 남겨 두고 열리는 순서대로 다시 쌓는다.

**③ 예비대가 cap ≤ 3 웨이브에는 아예 안 걸렸다** (codex·Claude 공통, 재현됨)
`onTime = ceil(cap × 0.75)`는 cap 1·2·3에서 `onTime === cap`이 되어 **예비대가 0기**다.
12판은 웨이브 8개 중 4개가 이 사각지대였다 — 주석은 "뒤쪽 25%"라는데 실제로는 안 걸렸다.
**주석이 코드보다 많은 것을 주장하고 있었다.** → cap 1(수문장)만 예외로 두고 2 이상은 최소 1기 보장.

**④ 진행도를 넘겨도 다음 폴링까지 기다린다** (codex, 재현됨)
차단될 때 `spawnNext = t + s.every`로 미뤄서, 진행도를 넘긴 뒤에도 `every`초를 더 기다렸다.
그 사이 판이 끝나면 **영영 안 나온다**(실측: COVER 0.9에서 16기 중 2기 미출전).
→ 미루지 않고 매 프레임 다시 본다. 이게 앞선 튜닝이 헛돌던 진짜 이유였다.

**⑤ `sweeps` 카운터가 안 그려도 증가한다** (Claude)
`shotsFired`는 `reduceMotion`이면 안 세는데 `sweeps`는 셌다. 검수 하네스가 "연출 났다"로 오판할 수 있다.

**⑥ 아주 좁은 가로(667×375, 아이폰 SE 2·3세대)는 여전히 잘린다** (codex, 계산으로 지적 → 실측 확인)
→ 700px 미만에서는 숫자패드를 4열 3줄로 접는다. 측정: 232/232px **전부 보임**.
568×320(2016년 SE)만 21px 잘림으로 남았다(이전 209px).

**⑦ 미러 테스트가 예비대 거동을 못 잡는다** (codex)
프로브에서 예비대 조건문을 **통째로 지워도 통과**했다 — 개수만 보고 시점을 안 봤다.
→ 스폰 시점의 성 진행도를 대조한다(예비대 있음 최대 0.85·0.3 초과 7기 / 없음 0.38·2기).
지운 상태로 돌려 **실제로 실패**하는 것까지 확인했다.

## 13-2. 되짚어야 했던 것 — 게이트를 낮추지 않는다

③④를 고치자 G8-b가 하나 남았다: **정답 95% 아이 패배율 2.86%** (하한 3%). 630판 중 18패,
19패면 통과다. 0.14%p 차이라 임계값을 건드리고 싶은 유혹이 컸지만, 이 게이트는 사용자가
"너무 쉬워서 노잼"이라고 한 바로 그것을 잡으라고 만든 것이다. **게이트가 아니라 게임을 고쳤다.**

원인은 단계 표에 있었다. 단계 간 **배율**이 위로 갈수록 완만해진다:

```
현재:  ×1.70 → 1.53 → 1.38 → 1.33 → 1.29 → 1.26 → 1.23 → 1.21
```

그래서 상위 단계에서 한 칸 올라가도 별로 안 아프고, 적응 루프의 균형점(5.5단계)에서 거의 안 진다.
4단계부터 ×1.35로 고정했다 — **0단계는 손대지 않았다**(G2 안전망의 근거).

결과: 정답 95% 아이 패배율 **2.86% → 5%**, 성 피격 11% → 13%. 전 게이트 통과.

## 13-3. 걸러낸 것

- **codex WARNING "COVER 0.8까지 전원 배출 보장 없음"** — ④를 고치면서 근거가 사라졌다.
  이제 진행도를 넘긴 즉시 나온다.
- **Gemini 카피 대안 "N레벨까지 조각 M개 더!"** — 방향은 채택했지만 문장은 바꿨다.
  `M개 더 모으면 N레벨!`이 목표를 뒤에 두어 저학년에게 더 읽힌다.
- **Claude NIT "shots 상한 41 (off-by-one)"** — 사실이라 고쳤다(`> 40` → `>= 40`).
- **Claude "저사양 프로파일링 권장"** — 코드 리뷰만으로는 근거가 부족하다는 리뷰어 본인의 판단에
  동의한다. 기존 코드도 매 프레임 그래디언트를 만드는 같은 패턴이고, 새 배열은 비활성 시 즉시 반환한다.
  실기기 실측 전까지는 조치하지 않는다.

## 13-4. 이번에도 나온 것 — 주석이 코드보다 많은 것을 주장했다

③이 그렇다. `RESERVE_SHARE` 주석은 "뒤쪽 25%는 진행도로 나온다"고 단언했는데,
가장 흔한 입력 범위(cap 1~3)에서는 **한 기도 안 걸렸다**. 테스트도 통과했다 —
큰 cap 웨이브들이 대신 떠받쳐서 전체 지표가 목표를 만족했기 때문이다.
**집계 지표가 맞으면 구성 요소도 맞다고 믿으면 안 된다.**
"살아남은 것만 재면 전량 삭제를 못 본다"와 같은 함정이다.
